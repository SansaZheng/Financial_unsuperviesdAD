# Audit-HCL 填充索引性能核验

原参考实现把缺失邻居暂时映射到节点0，然后用遮罩使其注意力和梯度为0。这个写法数学上正确，但GPU反向索引累加会把大量无效槽位集中到同一行。优化实现将这些槽位映射到各自查询行，再按原遮罩归零；邻居集合、公式、随机采样和超参数保持不变。

[完整诊断结果](zero_label_padding_profile.json)和[固定源码的CQ规格](zero_label_padding_cq_spec.json)保留了可复核证据。测试使用合成特征及合成支付拓扑，不使用目标标签，也不计算金融AP/F1。小图比较同一权重的前向及梯度；4128节点图在预热后比较3次参数更新。

| Tesla T4，Torch 2.11.0+cu130 | 节点0填充 | 按查询行分散填充 |
|---|---:|---:|
| 三步拟合总时间（秒） | 21.064 | 5.312 |
| 扣除邻居表构造/传输（秒） | 20.217 | 4.554 |
| 峰值CUDA分配（GiB） | 0.787 | 0.787 |

本次小图前向、梯度及三步训练状态的最大绝对差均为0。扣除邻居表开销的诊断加速比为4.439，包含这些开销的总加速比约3.97。该单次微基准不代表所有金融任务的端到端加速比。另有CPU float64测试将填充实现与逐节点、无填充的有效邻居计算对照，验证前向和梯度。

诊断参考源码固定在 `960673f3a61a4c93fb5033ccbba8f8a3d670ccbd`，优化提交为 `8472386`。CQ规格中的依赖ID和输出目录属于本次执行记录；其他环境复跑时应调整作业依赖/路径，保持源码和内嵌测试内容一致。正式金融结果以各自 `run_manifest.json` 的提交为准，完整144次的同一队列作为一个整体核验和报告，不混用两种执行版本的记录。
